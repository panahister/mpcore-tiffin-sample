# Architecture

How Tiffin is cut into services, how they talk, and why. Every choice names where it comes from.

## Nine services, nine databases

Each bounded context is a service: it is built alone, it is started alone, and it owns its data. Eric Evans
named the *bounded context* (*Domain-Driven Design*, 2003); that each service owns a database of its own is
Chris Richardson's *database per service* (*Microservices Patterns*, 2018). On a developer's machine the
nine databases share one PostgreSQL server, to save memory; a service has the name of one database and
never reads another's.

| Service | Its aggregates | What it decides | What it never does |
|---|---|---|---|
| Access | `Grant` | who may have which role, in which city | keep people: the identity provider does |
| Media | `MediaFile` | what a file may be, and whether what arrived is what was announced | touch the bytes |
| Restaurants | `Restaurant` with its menu | what an order costs | know that an order exists |
| Ordering | `Order` | what happens next to an order, and what is taken back | charge, cook or carry |
| Payments | `Payment` | whether a card is charged | know what was ordered |
| Kitchen | `Ticket`, and a copy of each restaurant | whether the restaurant cooks | know what it costs |
| Dispatch | `Courier`, `Delivery` | who carries what | know where a courier is |
| Tracking | `TrackedDelivery`, and a time series of positions | who may say and see where a delivery is | decide anything about the delivery |
| Notifications | `Notification` | nothing: it tells | write to the stream |

**The services share no assembly.** There is no `Tiffin.Shared`, no `Tiffin.Contracts` that two services
reference. A shared assembly is a distributed monolith in waiting: the day it changes, every service that
references it is built and deployed again. What two services agree on is a message or a `.proto` file, and
each states it in its own code, with only the fields it uses. An architecture test in every service fails
when the service references another, and the contract tests hold the copies together.

## Inside a service

Every service was generated by `mpcore new backend` and has MP Core's layout:

```text
ordering/
  src/
    Tiffin.Ordering.Domain/           aggregates, value objects, rules, events. References MPCore.Domain only
    Tiffin.Ordering.Application/      commands, queries, handlers, ports, contracts. Knows ports, never a provider
    Tiffin.Ordering.Infrastructure/   adapters: Entity Framework, clients of other services, migrations
    Tiffin.Ordering.Api/              the host: endpoints, policies, queues and topics, Program.cs
  tests/
    Tiffin.Ordering.Tests/
```

The direction of dependencies is Robert C. Martin's *Dependency Rule* (*Clean Architecture*, 2017); the
ports are Alistair Cockburn's *Hexagonal Architecture* (2005). A handler is a static method that takes its
ports as parameters, so a rule is tested in microseconds with no container.

### What the generator wrote, and what was added

| The generator wrote | Added by hand, to every service |
|---|---|
| The four projects, the host's pipeline, security, health, failure handling, the message catalogue, the design-time factory for migrations, skills for AI agents | `appsettings.Development.json`; a user-secrets identifier; migrations on start in Development; a test project |

The second column is a proposal for MP Core's template: [findings](findings.md), T-03.

## How the services talk

Three ways, each for what it is good at.

| Way | For | Here | Pattern |
|---|---|---|---|
| A call, while somebody waits | a question whose answer has to be true now | Ordering asks Restaurants what an order costs (REST), and hands the card's token to Payments (gRPC) | *Request-Reply* |
| A queue | a request to one service, and its answer | the five requests and seven answers of the order process, on RabbitMQ | *Point-to-Point Channel*, *Command Message* |
| A stream | what happened, for whoever wants to know | the events of orders, deliveries, restaurants, roles and files, on Kafka | *Publish-Subscribe Channel*, *Event Message* |

The patterns are Gregor Hohpe's and Bobby Woolf's (*Enterprise Integration Patterns*, 2003).

**One channel per contract**, named after the reader, the contract and its version:
`tiffin.payments.payment-requested.v1`. The services share no assembly, so a message carries no type name
that both sides know; the channel says which contract it carries, and each side reads it as its own
declaration of that contract.

### A call costs availability

Ordering cannot place an order while Restaurants is down. That is a decision: the alternative is a copy of
every menu in Ordering, kept from events, which lets Ordering work alone and charge a price that changed a
second ago. Martin Fowler calls the copy *event-carried state transfer*. Tiffin uses both, each where it
fits:

| | Asked, while somebody waits | Copied, from the stream |
|---|---|---|
| What | the price of an order | which restaurants exist, and who manages them |
| Who | Ordering asks Restaurants | the Kitchen reads the stream of Restaurants |
| Because | a price is charged, and has to be the one that is true now | a manager changes once a year; a copy that is a second old is right |
| The cost | no order while Restaurants is down | the Kitchen knows a new restaurant a moment late |

### A service calls as itself

A call from one service to another carries a token the identity provider issued to the calling service: the
OAuth 2.0 *client credentials* grant (RFC 6749, section 4.4). The called service validates it like any
token and sees a caller of kind "service", with the role `service` and no city. So:

- the endpoint that prices an order is for services only, and refuses a customer's token whatever its role;
- Payments has no route at the edge at all;
- **the city travels in the request**, because a service's token names none. Payments believes it because
  it believes the caller. Whether MP Core should carry the tenant of a call between services, as it carries
  the tenant of a message, is an open decision: [findings](findings.md), T-05.

## The order process

An *orchestration-based saga* (Hector Garcia-Molina and Kenneth Salem, *Sagas*, 1987; Chris Richardson,
2018), which Hohpe and Woolf call a *process manager*. No framework type: the state of the process is the
`Order`, and each answer is one handler, one transition and at most a few messages, in one transaction.

**Orchestration, not choreography.** In a choreography each service reacts to the events of the others and
nobody knows the whole. Here one class does, `OrderProcessHandler`, and the question "what happens when the
restaurant refuses" has one place where it is answered.

**Every answer can arrive late, twice, or after the order was cancelled.** A handler asks the order first
(`CanMarkPaid`, `CanAccept`) and ignores what no longer applies. A charge that arrives for a cancelled order
is paid back; a restaurant's yes for a cancelled order tells the Kitchen to stop once more.

**A request that is given up is an answer too.** A request that ends in the error queue answers nothing,
and the order would wait for ever. So the host's error policy, where a message is given up, sends the
answer "declined" or "nobody can carry it" in its place.

**What the process cannot do yet:** wait no longer than so long. An order whose restaurant never answers
stays paid. [Findings](findings.md), T-08.

## Two cities

The city is the tenant, and it is in four places.

| Where | How |
|---|---|
| The token | Keycloak writes the `tenant_id` of the group somebody is in. MP Core reads it, never from a header or a route |
| A message | MP Core writes the tenant of the work that publishes into a header, and opens it for the handler that receives the message, save included |
| A row | every table has a `City`; every repository asks for it in its signature, so a read without a city does not compile |
| The audit trail | MP Core records the tenant of every record |

The second row is new in MP Core `0.9.1`, and Tiffin is why: [findings](findings.md), T-01.

## Access, in front of the identity provider

An *anti-corruption layer* (Evans). Keycloak speaks of realms, groups, paths and role mappings; the platform
speaks of cities and roles. One adapter translates, `KeycloakDirectory`, and nothing of Keycloak's language
passes its port.

**It is on the path of administration, and on no other.** Somebody signs in at Keycloak, not at Access.
Every service validates tokens itself, with Keycloak's public keys. Access is asked when a role changes,
which is rare, so Access being down stops nobody from ordering.

**Nobody else can do what it does.** The service account of Access holds the roles of Keycloak's
`realm-management` that its calls need. No other service account holds any, so another service that called
Keycloak's administration would be refused by Keycloak, whatever its code says.

**Two systems, no transaction across them.** A decision is recorded with a message that says "apply it", in
one transaction; the message tells Keycloak afterwards and marks the decision applied. To give a role
somebody has changes nothing, so the step is safe to repeat. Pat Helland (*Life beyond Distributed
Transactions*, 2007) names what such a step needs: idempotence.

## Media, the one place for files

Every other service keeps the identifier of a file. The bytes go from the app to the store and back, over an
address Media signed for a few minutes: the *presigned URL* of the S3 API. Media is asked twice per file,
with two small requests, whatever the size of the file.

An address that was signed can be used for anything that fits the signature. So a file is available only
after Media asked the store what arrived, and it is what was announced (rule M5).

The store is a setting: [variations](variations.md).

## What a log may show

A record that holds personal data or a credential says what it prints. Wolverine logs a message whose
handling failed by printing it, and a C# record prints every property.

| Never printed | Where it is |
|---|---|
| The token of a card | `PlaceOrder`, `OpenPayment`, `Payment` |
| A recipient, a phone number, a door | `DeliveryAddress`, `CourierRequested`, `Destination` |
| Where a courier was | `Position`, `ReportPosition` |
| A signed address | `UploadTicket`, `MediaView` |
| A client secret | `OtherServices`, `ServiceIdentity`, `S3Options` |

A test holds each line of the table, and the contract tests hold every message that crosses a service.
